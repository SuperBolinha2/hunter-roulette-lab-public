# Developer-facing material shipped with the game

This note records only evidence read from the purchased local installation.
The original tree was not modified. Paths under `Game\Client_Data` refer to
`<ORIGINAL_GAME_ROOT>`.

## What is and is not present

- `[CONFIRMED]` No loose `README`, changelog, protocol specification, design
  document, or server-maintenance manual was found in the 1,300-file install.
- `[CONFIRMED]` The build does ship machine-readable update metadata,
  generated protobuf descriptors, readable Lua battle logic inside an asset
  bundle, configuration tables, and many developer comments. Together these
  are substantially more useful than a human-facing note for reconstructing
  the client contract.

## Update/hotfix mechanism

`StreamingAssets\PkgVersion.json` contains explicit update controls and
version slots, including `mIsOpenUpdate=true`, `mIsOpenPreUpdate=true`,
platform/fight resource versions, backup/pre-update versions, code version,
CDN directory metadata, and network timeout settings.

The resource trees also contain per-bundle manifests:

- `AssetBundles\PC\fight\ResBundles\AssetBundleHotMd5.json`
- `AssetBundles\PC\platform\ResBundles\AssetBundleHotMd5.json`
- `AssetBundles\PC\Other\VideoHotfixInfo.json`

The fight manifest has 82 bundle entries with bundle name, MD5, and size;
`fight_dbconfig.ab` is one of the named hot-update units. This proves the
client was built to version and verify replaceable resource bundles. It does
not document the unavailable server implementation.

## Protocol and battle contract

Canonical original bundle:
`AssetBundles\PC\fight\LuaBundles\lua.ab`.
The readable extraction used for indexing is documented in `LUA_MAP.md`.

High-value shipped files:

| File inside `lua.ab` | Confirmed evidence |
|---|---|
| `00other\system\common\pb\lua%pvp_pb.bytes` | Generated protobuf field numbers/types for PVP messages. Header says it was generated by `protoc-gen-lua` and must not be edited. |
| `00other\system\common\idedescription\lua%config_description_1.bytes` | Developer annotations for enums and fields, including ammo, final-source events, PVP statuses, and event timing. |
| `umodel\roulettegame\lua%clientanimexpression.bytes` | Exact routing of shoot events, `OnFire`, ammo consumption, final-source handling, prepare queuing, and `OnShootOver`. |
| `umodel\roulettegame\lua%roulettegameplayer.bytes` | HP/ammo/UI update rules and timestamp guard. |
| `umodel\roulettegame\lua%roulettegamemodule.bytes` | PVP event/next-round handlers and `Pvp_Prepare -> PvpIng` transition. |
| `_single` roulette-game scripts | Fully local/tutorial player, AI, shot, and turn flow; AI waits 3 seconds before acting. |

Confirmed field semantics from the shipped annotations/code:

- `PvpEventOutline.ammo`: ammo used by shooting/adding ammo.
- `PvpEventOutline.rAmmo`: authoritative full ammo list.
- `PvpEventOutline.cAmmo`: ammo-type change, not ordinary consumption.
- `PvpEventOutline.uTime`: event update time.
- `PvpEventSmall.Enum_Shoot = 2`.
- `PvpEventSmall.Enum_Finally_Source = 3`, described as the final source
  event. `gamerStatus` belongs only in that final event.
- `PvpStatus.PvpIng = 2`, `PvpStatus.Pvp_Prepare = 3`, `PvpEnd = 4`.
- `ClientAnimExpression.OnFire` calls `ShootAmmo` before applying the source
  and target outlines. `ShootAmmo` performs the visible decrement.
- The client stores `Enum_Finally_Source`, applies it at `OnFire`, and queues
  a prepare notification until the shot callbacks have completed.

## Timing values recovered from `fight_dbconfig.ab`

- self-shot normal wait: 1500 ms
- alternate self-shot wait: 800 ms
- shoot-other wait: 300 ms
- post-reload interval: 900 ms

These are pre-animation/configured waits, not proof of total animation length.

The same decoded `normal_const_parameter_int` table contains `game_init_time=5`
and `reload_show_time=1`. The active `RouletteBattleWindow:OnGameStart_New`
path does not use those values for its internal opening cadence: its Lua timers
are 1 s to ammo HUD, then 3 s to `SetAmmo(..., true)` (reload), then 2 s to
`playerInit`, then 5 s to clear the opening state. The resulting reload begins
about 4 s after the table ammo appears. Server v15 delays the first active-turn
packet to 11 s but cannot extend that client-side reload interval.

For the frozen gold/bag-like visual, the shipped Lua has two distinct routes:
coin changes call `RouletteGameScene:UpdatePlayerCoin` (gated by
`isShowPlayerCoin`), while a carried card calls `PlayerCardShow` from
`SetCardSlot`. The native C# `SceneController:UpdatePlayerCoin` implementation
is not present in the IL2CPP stub dump, so Lua alone cannot identify the exact
3D mesh or prove which asset it instantiates.

## Consequence for the local server

The prior emulator incorrectly sent `cAmmo` for every shot, omitted
`Enum_Finally_Source`, skipped the explicit prepare phase, and could announce
round 2 while embedded gamers still carried round 1. Server v12 now follows
the shipped client contract for those four points. A localhost integration
test confirmed the sequence and protobuf fields; visual gameplay remains a
separate live validation.
